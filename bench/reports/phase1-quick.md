## 1. 摘要

第一阶段是正式实验前的探路运行，用于检验方向是否成立、评测流程是否可靠。结果不直接用于论文。

主要发现：

1. **让语音模型直接操作文档不可靠。** R1（Boson 实时模型直接调用文档工具）成功率 20.0%，误改率 41.7%；S3 分别为 66.7% 和 5.0%。60 道题中，S3 优于 R1 的有 29 道，R1 优于 S3 的仅 1 道。
2. **语音模型直接操作并不更快。** R1 与 S3 的完成时间差异不显著（整轮结束时间中位数差 −0.64 秒，95% 置信区间 [−1.34, +0.14] 秒）。原设计中"响应快但做不对"的表述，应调整为"做不对，且并不更快"。
3. **预读优化有效且不损失准确率。** 关闭预读后，整轮结束时间中位数增加 1.24 秒（95% CI [+0.51, +2.18]），最后一次写入时间增加 1.06 秒（95% CI [+0.55, +1.97]），模型请求次数由平均 2.78 次增至 4.22 次；成功率差异不显著（+3.3%，95% CI [−8.3%, +16.7%]）。
4. **S3 的失败大多来自治理确认，而非能力不足。** S3 的 20 次失败中，有 12 次的主要原因是服务端治理规则要求先征得用户确认；评测协议只发送一条指令、无人回答确认，因此记为失败。若确认后正确执行，S3 成功率上限约为 88%（53/60）。

尚不能得出的结论：本阶段未包含 S2（同模型单 Agent），因此**论文的核心论点——同一模型下 Actor-Worker 架构优于单 Agent 架构——尚无数据**，需第二阶段验证。

## 2. 实验目的

1. 检验 S3 在标准编辑任务上能否稳定完成；
2. 检验"语音模型直接操作文档"作为对照的表现，为论文动机提供依据；
3. 测量预读（`VDOC_SERVER_WORKER_PREFETCH`）对时间和准确率的影响；
4. 验证评测宿主、判分器和计时在真实模型下可靠。

## 3. 实验设置

### 3.1 系统配置

| 配置 | 架构 | 执行模型 | 关键设置 | 在论文中的角色 |
| --- | --- | --- | --- | --- |
| **S3** | Actor-Worker：Boson Higgs 只负责听和说，Pi Worker 负责判断和工具调用 | Claude Haiku 5.5 | 关闭思考；预读 `read_document` 与 `get_context`；提示缓存开启 | 被测系统 |
| **S3-noprefetch** | 同 S3 | Claude Haiku 5.5 | 关闭预读，由 Pi 自行读取 | 消融：预读的贡献 |
| **R1** | Boson Higgs 实时模型直接调用文档工具，无 Agent 循环 | Boson Higgs | 服务端 `boson` 模式 | 动机参考（模型不同，不作公平对比） |

三个配置使用同一套 vdoc 文档工具、同一套服务端治理规则和同一份初始文档。

### 3.2 任务

- 来源：VDocs-Bench v1.0.0-draft 主任务集。
- 子集：`bench/tasks/paper-60.json`，从 6 类编辑任务中各抽 10 道，单步、多步各 5 道，固定种子 261026。写作类任务不在其中。

| 类别 | 代号 | 题数 |
| --- | --- | --- |
| 文字格式 | FMT | 10 |
| 大小写与替换 | REP | 10 |
| 移动与删除 | MD | 10 |
| 段落与结构 | STR | 10 |
| 指代与定位 | REF | 10 |
| 多处同时修改 | MULTI | 10 |

### 3.3 运行方式

- **输入**：文字输入，跳过语音识别。
- **重复与顺序**：每题每配置 1 次；在每道题内按种子 261026 随机排列三个配置的运行顺序，使三者在同一时段交替运行。
- **会话**：每次运行使用全新文档和全新语音会话。任务含固定历史时，先作为前序用户轮次发送。
- **宿主**：评测宿主在本地无头运行 vdoc 自身的编辑引擎与实时文档工具（vdoc `31273d1e`），工具语义与真实编辑器一致。服务端在同一进程内启动，通过真实 HTTP 与 WebSocket 连接。
- **结束判定**：智能体空闲且无进行中的工具调用并持续 1.5 秒后，读取最终文档；再观察 2 秒检查迟到写入（本阶段为 0 次）。
- **超时**：60 秒。

### 3.4 判分

- **成功**：最终文档与参考答案在文字、逐字符样式、块类型、标题层级、列表结构和块顺序上完全一致，且无误改。
- **误改**：改动了参考答案保持不变的内容。漏改不计为误改。
- **部分完成率**：已满足的步骤数 / 总步骤数。
- **置信区间**：按题重抽样的 95% 自助法区间（2000 轮）。
- 判分器已用 105 份参考答案验收：正确答案全部判为成功；未改动的文档全部判为漏改且无误改；在受保护内容上的人为改动 103 例全部被识别。

### 3.5 时间指标

所有时间从发送文字指令起计，单位毫秒。未发生的事件不计入，不按 0 处理。

| 指标 | 含义 |
| --- | --- |
| 首次写入 | 第一次成功修改文档 |
| 最后一次写入 | 最后一次成功修改文档，即文档改完的时刻 |
| 整轮结束 | 智能体回复与朗读结束，进入空闲 |

## 5. 分析

### 5.1 治理确认对结果的影响

服务端治理规则把以下操作评为高风险，执行前须由用户确认：

| 触发确认的操作 | 次数（三个配置合计） |
| --- | --- |
| `text.findReplace`（查找替换） | 25 |
| `text.findReplace` 与样式操作在同一次调用中 | 5 |
| 一次删除多个块（`block.delete` ×2 及以上） | 2 |
| 风险表中未登记的操作（`block.style`、`paragraph.insert`，按规则一律视为高风险） | 3 |
| **合计** | **35** |

S3 遇到这类情况时会正确地向用户提问，例如"需要确认一下：是否把第四段的'周五'替换为'周四'？"。这在真实使用中是正常的两轮交互，但本阶段评测只发送一条指令，因此记为失败。

这也解释了"大小写与替换"类成功率偏低（20%）：Pi 即使只替换一处，也倾向于使用查找替换（`text.findReplace`），从而触发确认。改用只替换指定位置的 `text.replace`（中风险）可避免大部分确认。这是系统层面可以改进的地方，但不在本实验范围内。

**按"成功或已正确请求确认"计算的上限估计**：S3 为 88.3%（53/60），S3-noprefetch 为 91.7%（55/60），R1 为 28.3%（17/60）。该上限假设确认后都能正确执行，需第二阶段实测。

### 5.2 R1 的失败模式

R1 的误改多为**字符范围偏差**。例如"只把第二段的'一楼会议室'标黄"，结果多标或少标了相邻的几个字；"第二段第一句加下划线"，结果改动了 22 个不该改的字符。此外有 4 次因调用工具过多触发每轮 12 次的上限，2 次因版本过期（STALE）写入失败。这与"语音模型缺少 Agent 循环、难以精确定位和自我纠错"的假设一致。

### 5.3 S3 的真实错误

排除确认因素后，S3 的错误有以下几类：

- **字符范围差一到两个字**：例如句子样式少覆盖句号，日期只加粗了一个字。
- **"正文"误包含了标题**：例如 MULTI-008，把标题里的词也标黄了。
- **列表结构不符**：STR-007 要求只把前两段转为编号列表，生成的列表结构与参考答案不一致。
- **多步任务第二步未完成**：MD-013 要求"移到开头再加粗"，移动后 Worker 失败，加粗没有执行。

### 5.4 关于 R1 的定位

R1 与 S3 使用的模型不同（Boson Higgs 对 Claude Haiku），且 R1 没有 Agent 循环，因此两者的差距不能归因于架构。本阶段的 R1 数据只用于论文动机，说明"让语音模型自己操作文档不可靠"。架构层面的证据需由第二阶段同模型的 S3 与 S2 对比提供。

## 6. 局限

1. **每题只运行 1 次**，无法估计运行间波动；按类别的结果每格仅 10 次。
2. **未包含 S2**，无法回答核心的架构对比问题。
3. **只测了文字输入**，未包含语音识别与真实语音时序。
4. **未包含写作类任务**。
5. **评测协议不回答确认**，低估了 S3 和 S3-noprefetch 的实际完成能力。
6. **单机单网络**：所有运行在同一台机器、同一网络环境下完成，延迟包含到 Anthropic 与 Boson 的网络时间。
7. **偶发英文混杂**：Pi 的回复偶尔夹杂英文句子（如 "Should I replace …"），违反"不要自言自语"的规则。不影响判分，但影响用户体验。

## 7. 对第二阶段的调整

| 项目 | 第一阶段 | 第二阶段 |
| --- | --- | --- |
| 配置 | S3、S3-noprefetch、R1 | 增加 **S2**（同为 Haiku 5.5，编辑规则、思考设置、提示缓存均与 S3 对齐） |
| 重复 | 1 次 | 2 次 |
| 确认处理 | 不回答 | 系统请求确认时由评测统一回答"确认"，同时保存请求确认时的文档并单独判分，**严格口径与确认后口径都保留** |
| 主要速度指标 | — | 以"最后写入时间"为主：S3 与 S2 的朗读引擎不同（Boson 对 OpenAI 语音合成），整轮结束时间会混入朗读速度差异，仅作参考 |
