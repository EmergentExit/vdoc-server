## 1. 摘要

本阶段回答论文的核心问题：**在同一个模型（Claude Haiku 5.5）、同一套编辑规则和思考设置下，Actor-Worker 架构（S3）是否比单 Agent 架构（S2）更快，并且同样准确？**

| 结论 | 证据（中位数差，95% 置信区间） |
| --- | --- |
| **S3 明显更快** | 改完文档（最后一次写入）快 **3.10 秒** [1.99, 4.42]；首次写入快 **3.89 秒** [2.95, 4.43]；整轮结束快 **5.23 秒** [4.27, 7.22] |
| **去掉预读后，仅架构本身仍更快** | S3-noprefetch 对 S2：改完文档快 **1.88 秒** [0.87, 2.74]，首次写入快 2.46 秒 [1.55, 3.09] |
| **准确率无显著差异** | 成功率 S3 72.5%、S2 79.2%，差 +6.7% [−1.7%, +15.8%]；误改率 S3 17.5%、S2 15.0%，差 −2.5% [−10.0%, +4.2%]。点估计略偏向 S2 |
| **预读稳定节省约 1.1–1.4 秒** | 首次写入快 1.43 秒 [0.75, 2.01]，改完文档快 1.11 秒 [0.46, 2.11]，准确率无显著差异 |
| **语音模型直接操作很不可靠，且并不更快** | R1 成功率 25.8%、误改率 42.5%；改完文档时间与 S3 无差异（+0.07 秒 [−0.70, +1.01]） |

**S2 慢在哪里**：单 Agent 级联每说一句话，都要等这句话的语音合成完成才能继续下一步操作；Actor-Worker 架构中 Worker 工作时不出声，没有这一等待。按时间拆分，S2 在改完文档前平均有 **2.2 秒**花在这种等待上，另外还多出约 1 次读取用的模型请求（S3 由服务端预读）。

本阶段同时发现三个**与架构无关、但影响成功率的实现问题**（见第 5.3 节）：

- Pi 调用模型时不会自动重试，偶发的网络中断导致 S3 系列 16 次 Worker 失败，S2 为 0 次；
- 模型对"只改某处"的替换也使用作用于全文、默认不区分大小写的查找替换，确认后造成误改；
- Pi 的公开回复中经常夹杂英文的内部推理。

修复第一个问题后，S3 的成功率预计会提高几个百分点（排除这类失败后为 75.0%，与 S2 相差 +4.2% [−3.8%, +12.3%]）。

## 2. 实验设置

### 2.1 系统配置

| 配置 | 架构 | 执行模型 | 关键设置 | 角色 |
| --- | --- | --- | --- | --- |
| **S3** | Actor-Worker：Boson Higgs 只负责听和说；Pi Worker 负责判断与工具调用；服务端拿到输入后直接启动 Worker | Claude Haiku 5.5 | 关闭思考；预读 `read_document` 与 `get_context`；提示缓存 | 被测系统 |
| **S2** | 单 Agent 级联：语音识别 → 同一个模型既回复又调用工具 → 语音合成（OpenAI） | Claude Haiku 5.5 | 与 S3 对齐：相同的编辑规则（vdoc 基础规则 + Worker 编辑规则）、关闭思考、不传 effort、提示缓存 | **架构对照（主证据）** |
| **S3-noprefetch** | 同 S3 | Claude Haiku 5.5 | 关闭预读 | 消融；也作为"仅架构不同"的对照 |
| **R1** | Boson Higgs 实时模型直接调用文档工具 | Boson Higgs | 服务端 `boson` 模式 | 动机参考（模型不同，不作公平对比） |

S2 的对齐在评测中完成，未修改服务端代码：评测替换了级联中 Claude 客户端发出的请求，使模型、编辑规则、思考设置和提示缓存与 S3 一致。每次请求的实际参数都记录在结果中，核对无误：两者都是 `thinking: disabled`、不传 effort、开启缓存、模型 `claude-haiku-5-5`。

### 2.2 任务与运行

- **任务**：`bench/tasks/paper-60.json`，6 类编辑任务各 10 道（单步、多步各 5 道），种子 261026；不含写作题。
- **输入**：文字输入。
- **重复**：每题每配置 2 次；在每道题的每次重复内，按种子随机排列 4 个配置的运行顺序，使各配置在同一时段交替运行。
- **宿主与判分**：与第一阶段相同。vdoc 自身编辑引擎在本地无头运行；判分要求与参考答案逐字符、逐结构完全一致且无误改。
- **确认**：当服务端治理规则要求用户确认时，评测发送"确认。"作为下一轮用户输入，每次运行最多 2 次。请求确认那一刻的文档另行判分，作为"无人确认"的严格口径。
- **统计**：置信区间为按题重抽样的 95% 自助法区间（2000 轮）。延迟比较取各配置全部运行的中位数之差；涉及"改完文档"与"整轮结束"的比较，只纳入未经过确认环节的运行（确认轮次会把时间拉长，且两种架构请求确认的频率不同）。

### 3.4 时间拆分：S2 慢在哪里

以下只统计未经过确认环节的运行，取中位数：

| 配置 | 改完文档用时 | 其中：模型生成 | 其中：工具执行 | 其中：等待 | 改完前的模型请求数 |
| --- | --- | --- | --- | --- | --- |
| S3（n=88） | 3.21 s | 3.17 s | 0.003 s | **0.03 s** | 2.02 |
| S3-noprefetch（n=91） | 4.31 s | 4.27 s | 0.004 s | **0.04 s** | 3.14 |
| S2（n=90） | 6.25 s | 3.94 s | 0.005 s | **2.21 s** | 3.17 |

- **S3 与 S3-noprefetch 的差距**来自模型请求次数：预读让 Worker 少发约 1.1 次请求，省约 1.1 秒。
- **S2 与 S3-noprefetch 的模型请求数相同**（都要自己读文档），模型生成时间也接近，但 S2 多出 **2.2 秒等待**。
- **等待的来源**：级联实现（`@vrealtime/cascade`）在每次模型回复结束前，会等待该回复中所有文字的语音合成完成（`await speaking`），然后才把工具结果交给下一轮。S2 按规则"先说一句再动手"（如"好的，我来改"），所以每一步都要等语音合成。S3 的 Worker 工作时不出声，只在最后由 Actor 朗读一次回复，因此没有这一等待。

这正是 Actor-Worker 架构的核心设计：**把"说"和"做"分开，说话不再阻塞做事**。

需要说明的是：单 Agent 级联若改为语音合成与工具执行并行，可以缩小这 2.2 秒；但只要同一个循环既要说又要做，就必须处理两者的先后关系。Actor-Worker 从结构上消除了这个问题。

## 5. 分析

### 5.1 论文可以支持的表述

1. 在相同模型、相同编辑规则与思考设置下，Actor-Worker 架构完成编辑显著快于单 Agent 级联：改完文档快 3.1 秒，整轮快 5.2 秒；即使去掉预读，仅架构本身仍快 1.9 秒。
2. 速度优势主要来自"说"与"做"的解耦：单 Agent 级联每一步都要等待自身语音合成，平均累积 2.2 秒。
3. 速度提升没有带来可测量的准确率损失：成功率与误改率的差异均不显著。
4. 预读（服务端在 Worker 启动前读取文档与上下文）稳定节省约 1.1–1.4 秒，且不影响准确率。
5. 让语音模型直接操作文档的成功率仅约 1/4、误改率超过 40%，且并不更快。

### 5.2 论文不能支持的表述

- **"S3 比 S2 更准确"**：点估计反而略偏向 S2（+4 至 +7 个百分点），置信区间包含 0。合适的表述是"准确率相当，没有显著损失"。
- **"语音模型直接操作快但不准"**：两个阶段中 R1 都没有显著更快。合适的表述是"不准，而且不更快"。

### 5.3 与架构无关的实现问题

**问题 1：Pi 调用模型时不会自动重试。**

- **现象**：三个使用 Claude 的配置遇到连接中断的频率相近（约 1–2% 的请求在几十毫秒内断开）。S2 使用的 Anthropic 官方 SDK 默认自动重试，5 次中断全部恢复；Pi 的模型库在服务端调用时没有设置重试次数，一次中断就导致整个任务失败。
- **影响**：S3 与 S3-noprefetch 各有 8 次运行以 Worker 失败结束（S2 为 0 次）。其中多数可追溯到一次没有 HTTP 状态、几十毫秒即断开的模型请求；评测当前未记录这类错误的具体信息，下次运行会补上。
- **建议**：在服务端调用 Pi 时为可重试的连接错误开启重试（尚未产生输出的请求重试是安全的），并以此修复重跑。

**问题 2：模型用全文查找替换处理"只改某处"的请求。**

- **现象**：vdoc 的 `text.findReplace` 作用于全文，且默认不区分大小写。模型在"只把第二段的 AI 替换为人工智能，保留小写 ai"这类任务中仍使用它，触发治理确认；确认后会把其他段落、标题或小写形式一并替换。
- **影响**：S3 的 21 次误改中，有 10 次发生在确认之后，只有 1 次在确认前已存在。S2 与 S3-noprefetch 情况相同。这是两种架构共用的模型与规则造成的，不影响架构对比。
- **建议**：在编辑规则中要求对指定位置的替换使用 `text.replace` 并给出目标范围，只有"全文所有"类请求才用查找替换；必要时显式设置 `caseSensitive: true`。

**问题 3：Pi 的公开回复夹杂英文内部推理。**

- **现象**：例如 "The second body paragraph is p2 … I'll apply the red color"。这违反了 Worker 规则"不要把推理写进公开文字"。
- **影响**：不影响判分，但会显示给用户，部分情况下也可能被朗读。
- **建议**：调整 Worker 提示词，或在朗读前过滤非用户语言的中间文字。

## 6. 局限

1. **仅文字输入**：未包含语音识别与真实语音时序。S2 的语音合成使用 OpenAI，S3 使用 Boson，整轮结束时间混入了不同朗读引擎的差异；因此主速度指标采用"改完文档时间"，它与朗读引擎无关。
2. **每题 2 次重复、60 道编辑题**：可检测数秒级的速度差和较大的准确率差；不足以检测 5 个百分点以内的准确率差异。
3. **未包含写作类任务**。
4. **确认协议**：评测在请求确认后立即回答"确认"，没有人类的思考时间；"无人确认"口径单独报告。
5. **实现问题未修复**：第 5.3 节的三个问题都会影响成功率；问题 1 主要影响 S3 系列。
6. **单机单网络**：延迟包含到 Anthropic、Boson 与 OpenAI 的网络时间。
